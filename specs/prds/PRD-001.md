# Product Requirements Document

## 1. Vision And Problem

### Vision

Provide LLM coding agents with a deterministic, offline gatekeeper for creating,
validating, and promoting SDD artifacts through their permitted lifecycle states.

### Problem Statement

The SDD workflow identifies `promote-artifact` as the sole lifecycle authority,
but no executable validator currently enforces frontmatter schemas,
identifiers, relationships, prerequisites, transitions, or packet readiness.
Agents and humans can therefore create malformed artifacts or edit statuses
directly without reliable detection.

### Why Now

The SDD audit identified lifecycle enforcement as a correctness and auditability
gap. A repository-local CLI can make the workflow executable and provide the same
validation behavior locally and in CI.

## 2. Target Personas And Journeys

| Persona | Need | Relevant journey |
| --- | --- | --- |
| LLM coding agent | Create and advance valid SDD artifacts without bypassing workflow rules | Allocate an ID, author a draft, validate it, promote it through permitted states, check packet readiness, and respond to diagnostics |
| Existing CI system | Enforce repository-wide artifact integrity | Run `sdd validate --all --strict` and fail the check for invalid artifacts, relationships, transitions, or readiness conditions |
| Human reviewer | Review the content and identity associated with a promotion | Review the proposed artifact changes and actor metadata recorded by `sdd promote` |

## 4. Functional Scope And Epics

### In Scope

| Epic ID | Epic | Outcome | Depends On |
| --- | --- | --- | --- |
| EPIC-001 | Deterministic artifact validation | Agents and CI can validate supported artifacts, frontmatter, placeholders, IDs, and references | None |
| EPIC-002 | Identity and relationship integrity | IDs are unique and relationships among PRDs, epics, packets, dependencies, schemas, and releases are verifiable | EPIC-001 |
| EPIC-003 | Lifecycle promotion and readiness | Agents can perform valid transitions and obtain a read-only Spec-Ready result | EPIC-001, EPIC-002 |
| EPIC-004 | Agent and CI command interface | The same local CLI supports agent workflows and platform-neutral CI enforcement | EPIC-001, EPIC-002, EPIC-003 |

### Capability Boundaries

The CLI will provide:

- `sdd validate --all --strict`
- `sdd validate specs/001-feature/`
- `sdd check-ready specs/001-feature/`
- `sdd promote <artifact-or-packet> --to <state> --actor <name>`
- `sdd allocate-id <prefix>`

Validation will cover supported workflow artifact types, frontmatter schemas,
required fields, status values, IDs, uniqueness, collisions, placeholders,
blockers, prerequisites, dependencies, parent and epic links, cross-references,
schema links, approval metadata, and verification evidence.

`check-ready` will calculate the Spec-Ready Predicate as a read-only result.
`spec-ready` will not be persisted as an artifact status.

`promote` will be the only supported status-mutating command. It will update
status and promotion metadata in frontmatter, including the source state, target
state, actor, and promotion timestamp. It will not move files.

`allocate-id` will print the next available identifier without reserving it.
Later validation and promotion operations will detect collisions.

The MVP transition rules and schemas will be fixed in the CLI. A future version
may support a repository-defined DSL for states and transitions.

The CLI will emit actionable human-readable diagnostics and machine-readable
output.

## 5. Non-Functional Requirements

| Requirement | Target or constraint | Rationale |
| --- | --- | --- |
| Determinism | Validation and allocation produce consistent results for the same repository state | Reliable agent and CI behavior |
| Offline operation | No network, hosted service, or AI dependency | Usable in isolated repositories and CI |
| Repository boundary | Operates only on the current repository's local `specs/` tree | Prevents accidental cross-repository mutation |
| Platform support | Linux and macOS | Required local agent environments |
| Implementation language | Rust, following `specs/CONSTITUTION.md` | Project engineering constraint |
| Mutation safety | Promotions are atomic and collision-safe | Prevents partial or conflicting lifecycle changes |
| Diagnostics | Invalid operations return non-zero exit codes with actionable context | Agents need to correct failures |
| CI compatibility | Existing CI systems can invoke the same CLI used locally | Avoids local/CI policy divergence |
| Performance | Fast enough to run on every pull request | Required for CI enforcement; exact threshold TBD |

## 6. Assumptions And Out Of Scope

### Assumptions

- The current `specs/SDD_WORKFLOW.md` defines the supported artifact types, statuses, readiness predicate, and lifecycle policy.
- `specs/templates/` is source material and is not treated as active project content.
- The MVP command is available as a preinstalled `sdd` executable.
- CI configuration and branch protection already exist or are managed outside this product.
- `--actor <name>` is sufficient promotion identity metadata.
- Human reviewers remain responsible for semantic product decisions, genuine approval, and meaningful tests.
- Promotion metadata is stored in the promoted artifact's frontmatter.

### Out Of Scope

- AI-based semantic review or product-decision judgment.
- Determining whether a human genuinely approved an artifact.
- Determining whether a test is meaningful.
- A hosted service, remote repository database, or network dependency.
- Repository-specific configurable schemas or transition DSLs in the MVP.
- Reserving IDs or coordinating concurrent ID allocation.
- Moving files during promotion or archiving.
- Providing CI-provider-specific workflow files.
- Implementing the SDD product workflow itself beyond the gatekeeper CLI.
