# ADR-005: Layered Validation Architecture And Parser Boundaries

## Context

Active SDD artifact validation combines pure rule evaluation with filesystem
access and parsing of YAML frontmatter, Markdown, and Gherkin. The validator
must remain deterministic, offline, read-only, and able to report every
per-file failure without coupling its domain rules to external formats.

## Decision

Use the constitution's layered Rust workspace for this feature:

- The domain layer owns normalized artifact data, validation rules, diagnostics,
  and ordering.
- The application layer owns orchestration and the `ArtifactSource` port.
- The filesystem adapter owns canonical path discovery, file reads, and parser
  integration.
- CLI composition and serialization remain outside this slice and are deferred
  to EPIC-004.

Use established parser dependencies only at the adapter boundary: `serde`, a
Serde-compatible YAML parser, `pulldown-cmark`, and `gherkin`. Use `thiserror`
for typed library errors. Versions and exact YAML package selection are subject
to the constitution's dependency audit before implementation.

## Alternatives Considered

| Alternative | Reason not selected |
| --- | --- |
| One monolithic validator executable | Makes filesystem, parsing, rules, and output inseparable and weakens pure testing |
| Hand-written parsers for all formats | Duplicates mature parser behavior and increases malformed-input risk |
| Put parser models in the domain layer | Couples domain behavior to external syntax and serialization concerns |
| Add a plugin rule architecture | Speculative for a fixed MVP artifact set and adds unnecessary abstraction |

## Consequences

### Positive

- Pure rule evaluation can be tested without filesystem or network doubles.
- Parser failures can be converted into path-based diagnostics at the boundary.
- Future CLI output formats can consume the same application report without
  changing validation rules.
- Dependency direction follows `app` to adapters to application to domain.

### Negative Or Tradeoffs

- The initial workspace has multiple crates before a CLI exists.
- Normalized boundary types require explicit mapping from parser output.
- Parser dependencies must be audited and pinned before code is added.

## Follow-Up Actions

- Establish the Rust workspace and pin the toolchain before implementation.
- Audit selected dependencies with `cargo deny` for licence, advisory,
  duplicate-version, transitive-weight, and unsafe-footprint constraints.
- Add tests for each parser boundary and cite `REQ-001` and `FR-*` identifiers.
- Revisit CLI composition and serialization under EPIC-004.
