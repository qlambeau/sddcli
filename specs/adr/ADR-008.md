# Architecture Decision Record

## Context

The Spec-Ready predicate must verify approved supporting schemas and complete
behavior coverage. The existing Rust model recognizes PRDs, epic briefs, packet
artifacts, and ADRs, but not the canonical `DB-NNN` and `TABLE-NNN` documents
defined by `specs/SDD_WORKFLOW.md`. The normalized Gherkin model also records
scenario count and step presence but does not distinguish happy, alternate,
failure, and boundary behavior.

EPIC-002 deferred schema relationships until schema artifact contracts existed.
US-008 now provides that contract and requires schema-aware readiness checks. The
feature also needs a deterministic way to evaluate behavior coverage without
semantic AI judgment.

## Decision

1. Extend the existing normalized artifact model with `Database` and `Table`
   kinds at the canonical paths `specs/schema/DB-NNN.md` and
   `specs/schema/TABLE-NNN.md`.
2. Reuse the existing frontmatter and Markdown parser boundary, adding required
   schema metadata, headings, path identity, expected target kinds, and strict
   bidirectional database/table link validation in the domain rules.
3. Preserve schema documents as repository specifications only. Do not add a
   runtime database, SQL execution, migration engine, persistence port, or
   external dependency.
4. Extend normalized Gherkin feature data with scenario coverage categories
   derived only from exact, case-sensitive name prefixes:
   `Happy:`, `Alternate:`, `Failure:`, and `Boundary:`.
5. Make Spec-Ready evaluation require at least one scenario in every category.
   A scenario without a recognized prefix remains syntactically valid Gherkin
   but cannot satisfy a missing coverage category.
6. Keep schema and scenario-category evaluation in the existing domain and
   parser boundaries. Do not create a new architectural layer or a separate
   schema subsystem.

## Alternatives Considered

| Alternative | Reason not selected |
| --- | --- |
| Defer schema recognition to a later epic | Conflicts with the approved US-008 contract and the explicit decision to support schemas in this slice |
| Add a separate schema crate or database subsystem | Adds an architectural layer and runtime scope when normalized document validation is sufficient |
| Infer scenario categories from arbitrary words in scenario names | Keyword inference is ambiguous and can produce different results after harmless wording changes |
| Use Gherkin tags for coverage categories | The approved behavior selected exact scenario-name prefixes rather than a tag contract |
| Treat the scenario file as semantically complete without category checks | Cannot deterministically verify the four required coverage classes |

## Consequences

### Positive

- The readiness evaluator can verify schema references and behavior coverage
  deterministically and offline.
- Existing parser, snapshot, validator, discovery, and diagnostic boundaries are
  reused without a new crate or dependency.
- DB/TABLE links receive explicit target-kind and reciprocity checks.
- Scenario coverage is observable and testable without AI judgment.

### Negative Or Tradeoffs

- `ArtifactKind::ALL`, path identity, structural rules, relationship rules, and
  compatibility tests must expand from eight to ten recognized artifact kinds.
- Existing Gherkin normalized data and parser tests must change to carry coverage
  categories while preserving existing step-presence behavior.
- Authors must use the exact four scenario-name prefixes for a packet to become
  Spec-Ready.
- The readiness feature now owns a small amount of schema-document validation
  that was previously deferred by EPIC-002.

## Follow-Up Actions

- Extend domain artifact kinds, identity, structural rules, relationship target
  rules, and schema-link validation for DB/TABLE documents.
- Extend the parser and `FeatureSnapshot` with scenario category membership.
- Add domain, application, adapter, and scenario-equivalent tests before
  implementing the readiness evaluator.
- Keep schema templates excluded from active discovery and do not create runtime
  database state.
- Revisit CLI output and exit-code binding under EPIC-004.
