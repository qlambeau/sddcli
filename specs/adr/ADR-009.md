# Architecture Decision Record

## Context

US-009 must guard three completion transitions: supersession of approved
artifacts, release of approved release records, and archival of implemented
feature packets that `record-release` has already moved. The existing Rust
model recognizes packet, ADR, schema, and other SDD artifacts, but it does not
recognize `REL-NNN` release records or represent the `released` lifecycle state.
Release records are currently documented by a Markdown template whose included
features and verification evidence are observable repository content.

Without a normalized release-record representation, completion promotion would
need to trust caller-supplied facts or parse arbitrary Markdown inside the pure
domain layer. Both approaches would bypass the repository validation boundary
and make release and archival guards inconsistent with existing promotion.

## Decision

1. Add `ArtifactKind::Release` for canonical `specs/releases/REL-NNN.md`
   documents with the `REL-NNN` identity prefix and `release-record` type.
2. Add `LifecycleState::Released` and treat `released`, `archived`, and
   `superseded` as terminal completion states for promotion.
3. Extend the normalized document boundary with release-record data containing:
   - included feature user-story identifiers and their recorded statuses;
   - whether verification evidence is present; and
   - whether a release commit is present.
4. Resolve an archived packet's corresponding release record by its normalized
   `US-NNN` story identifier in the release's included-feature rows. The record
   must be structurally valid, `released`, and list the feature as `implemented`
   or `archived` before packet archival can be promoted.
5. Keep release-record creation, evidence compilation, and packet relocation in
   `record-release`. Completion promotion validates the already-relocated path
   and changes lifecycle metadata only.
6. Use the existing single-artifact promotion store for supersession and release
   records. Use a dedicated pure packet-archival plan with the existing atomic
   packet store for the five colocated packet artifacts; supporting ADRs are not
   archival participants.

## Alternatives Considered

| Alternative | Reason not selected |
| --- | --- |
| Leave release records outside the artifact model | Cannot apply canonical identity, structural, lifecycle, or promotion validation consistently |
| Trust caller-provided release and archival facts | Allows invalid completion transitions and makes guards dependent on unverified input |
| Parse raw release Markdown in the domain | Violates the pure normalized-domain boundary and couples business rules to source syntax |
| Move packets while promoting them to archived | Contradicts the approved workflow and gives two capabilities ownership of relocation and rollback |
| Archive every packet-context participant | Would incorrectly change supporting ADRs and other context artifacts |
| Introduce a runtime release database | Adds persistence and SQL scope that the approved feature explicitly excludes |

## Consequences

### Positive

- Release records participate in the same deterministic discovery, identity,
  validation, and lifecycle model as other recognized artifacts.
- Release and archive guards use normalized evidence rather than caller trust or
  AI judgment.
- Existing atomic source-conflict and packet-commit behavior can be reused.
- File relocation remains isolated to `record-release`, preserving a single
  owner for archive movement.
- The release/user-story association remains stable after packet relocation.

### Negative Or Tradeoffs

- `ArtifactKind::ALL`, structural rules, parser discovery, and compatibility
  tests gain a new recognized artifact kind.
- The normalized document model must carry release-specific data and reject
  malformed feature rows or incomplete evidence.
- Archive completion requires discovery of both archived packet content and
  released records in one evaluation.
- The latest promotion metadata remains a status audit record; release history
  and detailed evidence remain in the release document.

## Follow-Up Actions

- Extend domain artifact and lifecycle models and add normalized release data.
- Extend parser and filesystem discovery for canonical release records and
  archived packet paths.
- Implement pure release, supersession, and packet-archival guards with
  deterministic diagnostics.
- Extend application orchestration and existing promotion stores without adding
  a new crate or external dependency.
- Add domain, application, adapter, property, acceptance, and compatibility
  tests before implementation is considered complete.
